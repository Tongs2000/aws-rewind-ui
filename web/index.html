How to drive this

  1. Press the big button six times. It replays, in order: scan, plan --explain, diff, revert (dry run), revert --confirm, diff again to verify. space does the same thing.
  2. Undo it all (a) runs all six half a second apart — the one-click version, which is what rewind undo --confirm does in a single command. Click it again or press Esc to stop. The recording predates undo, so what the terminal pane shows is the commands it composes, each with its own real output.
  3. This is the output of a real run against a real AWS account, not a mock. Press t for the terminal pane: every command's own output, verbatim. If a number on screen is not in there, it did not come from rewind. (The transcript is demodata/session.txt, derived from the CLI's live-validation capture — demodata/derive.py states exactly what differs.)
  4. Step 1 names identities, not values. CloudTrail records what a call set; nothing in it says what the value was. That is step 2's job.
  5. The timeline is the session, one dot per change. Drag it and the table below shows what each field held at that moment; drag it to the far left for the before-values. It never moves on its own.
  6. The cards are grouped by what can be done about them. The top group — revertible, reverted, failed — is open; the rest are collapsed with a count and the reason: SKIPPED / DISCOVERED (CloudTrail recorded the change but not the value), UNCHECKABLE (no Describe plugin), UNREADABLE (the resource is gone). Click a header to expand one.
  7. Click a card for the evidence: the event id that proves the before-value, the change chain, the calls a revert would make, and at the bottom the CLI's own words for that field.
  8. Step 5 does not claim more than it knows. Four fields are REVERTED — written and confirmed by a read-back. Two are SUBMITTED: RDS applies Multi-AZ asynchronously and EC2's monitoring flag had not converged yet, so the tool reports accepted-not-settled. Step 6 shows both closed, which is how an asynchronous field is meant to be polled.
